# II

II는 Inverted Interview다. 사용자가 에이전트를 인터뷰하기를 기다리지 않고, 에이전트가 먼저 둘 사이에서 아직 논의되지 않은 것을 모두 찾아 질문으로 꺼낸다. 질문마다 예상 답을 붙여서, 사용자는 맞는지 확인하거나 틀린 것만 고치면 된다. 빈틈이 하나도 남지 않을 때까지 멈추지 않는다.

## 기준

예상 답은 지금 알 수 있는 사용자의 목적에 맞춰 고른다.

- WIW 의도 문장이나 `intent.md`가 있으면 그것을 기준으로 쓴다.
- 없으면 대화, 요청에 딸린 자료, 프로젝트 상태, 이전 세션에서 읽은 목적을 기준으로 쓴다. 의도 문서가 없다고 멈추거나 따로 만들라고 요구하지 않는다.

## 빈틈 찾기

빈틈은 다음 세 가지다.

- **논의되지 않은 전제**: 양쪽이 말하지 않은 채 다르게 짐작하고 있을 수 있는 것
- **정해지지 않은 점**: 결과를 만들려면 언젠가 정해야 하는데 아직 정하지 않은 것
- **부족한 점**: 요청이나 지금까지의 계획에서 빠졌거나, 약하거나, 그대로 가면 문제가 되는 것

요청을 구성 요소(만들 것, 단계, 화면, 데이터, 사람, 연결되는 시스템)로 나누고, 각 요소마다 아래 항목을 하나씩 대어 본다. 한두 개 떠오른 것으로 끝내지 않는다.

- 뜻이 둘로 갈릴 수 있는 말이나 목표
- 범위의 경계: 무엇을 하고 무엇을 하지 않는지, 기존 것은 어떻게 되는지
- 완료 기준: 무엇으로 확인하고 어느 수준이면 충분한지
- 서로 부딪치는 요구, 다른 프로젝트나 기존 규칙과의 충돌
- 아무도 말하지 않은 상황: 실패, 빈 데이터, 많은 양, 다른 기기, 다른 사람이 쓰는 경우
- 다시 쓸 수 있는 기존 자산이나 결과를 바꾸는 예전 시도
- 비용, 시간, 권한, 보안, 운영처럼 나중에 막힐 수 있는 조건

이미 대화나 의도 문서에서 정해진 것은 빈틈이 아니다. 파일·코드·세션·자료로 확인할 수 있는 것은 질문하지 않고 직접 확인해 예상 답의 근거로 쓴다. 확인한 결과가 기대와 다르면 그 차이를 새 빈틈으로 올린다.

## 질문하고 확인받기

빈틈마다 질문 하나와 예상 답 하나를 만든다. 예상 답에는 그렇게 본 근거(의도 문장의 어느 부분, 사용자의 말, 확인한 자료)를 붙인다.

맨 앞에 지금 이해한 목적을 한 문장으로 쓰고, 찾은 빈틈을 모두 번호를 붙인 표로 보인다. 결과를 많이 바꾸는 것부터 둔다. 많으면 구성 요소별로 묶되 빼지 않는다.

| # | 구분 | 아직 논의하지 않은 것 | 예상 답 | 근거 |

"구분"에는 위의 세 가지 가운데 하나(전제, 미정, 부족)를 적는다. 주제로 묶고 싶으면 표 사이에 구성 요소 이름을 소제목으로 둔다.

마지막 줄에 "맞으면 그대로, 틀린 번호는 고칠 내용만 알려 주세요"처럼 답하는 방법을 쓴다. 사용자가 답을 처음부터 지어내야 하는 열린 질문으로 끝내지 않는다.

확인을 받기 전에는 표의 답에 걸린 작업을 하지 않는다.

## 다 해소될 때까지 반복하기

- 사용자가 확인하거나 고친 답을 반영한 뒤, 그 답이 새로 만든 빈틈(새 범위, 새 조건, 바뀐 전제와 부딪치는 이전 답)을 다시 찾는다. 새로 찾은 것과 아직 확인받지 못한 것만 다음 표로 묻는다.
- 줄이 고쳐지면 그 줄에 기대 세운 다른 예상 답도 다시 맞추고, 바뀐 것은 다음 표에 다시 올린다. 이미 확인받은 것을 이유 없이 다시 묻지 않는다.
- 한 번 더 전체를 처음부터 훑어도 새 빈틈이 없고 확인받지 못한 줄도 없을 때만 끝낸다. 끝낼 때 "남은 빈틈 없음"과 함께 확정된 답 목록을 짧게 보인다.
- 작업을 시작한 뒤에도 새 결정 지점, 애매한 말, 충돌, 확인 결과가 기대와 다른 점이 나오면 같은 방식으로 다시 묻는다.

## 기록

`intent.md`가 있으면 확정한 답을 결정 사항에, 아직 남은 것을 미결 사항에 적는다. 확인한 답 때문에 원하는 것 자체가 달라지면 그 사실을 말하고, WIW 의도 문장이 있으면 함께 고친다.
